# Даты материалов и уведомлений

## Исправленные проблемы

| Приоритет | Проблема | Результат |
| --- | --- | --- |
| Высокий | Запоздавший исход мог перезаписать более свежий | Upsert сравнивает время события; эмиттер проверяет текущий статус источника |
| Средний | Повторная доставка меняла дату и снова делала уведомление непрочитанным | Одна доставка события не меняет время и отметки чтения; новая попытка меняет |
| Средний | Переименование меняло время завершения и длительность обработки | Отдельный `files.finished_at`, сбрасываемый при повторной обработке |
| Средний | Повторная проверка готового кейса поднимала старое событие в ленте | Ключ события учитывает состав и завершение материалов; `materials_updated_at` меняется только при изменении состава |
| Средний, frontend | «Вчера» вычислялось округлением прошедших суток; карточки устаревали | Календарные дни в часовом поясе устройства и общий таймер обновления |
| Минорный, frontend | Даты загрузки, завершения и консилиума выглядели как одно событие | Подписи действия и точное время с часовым поясом при наведении |

## Контракт API и хранения

- `files.created_at` — загрузка материала; `files.finished_at` — последний переход
  в терминальный статус. Повторная запись того же терминального статуса сохраняет
  `finished_at`, переход к обработке очищает его. Редактирование метаданных его не меняет.
- `notifications.occurred_at` — время события источника, в UTC.
  `created_at` **в БД** — первая запись уведомления; `updated_at` — запись нового исхода.
- В `GET /api/v1/notifications` поле `created_at` оставлено как совместимый
  псевдоним `occurred_at`. Старый фронтенд также показывает время события.
- Одна строка на `(section, entity_id, family)`. `occurrence_key` отличает новую
  попытку от повторной доставки. Вставка/обновление и сброс чтения атомарны.
- Готовность кейса датируется максимумом времени изменения состава и завершения
  его материалов. Переименование, теги и приватность не меняют дату готовности.
- Лента сортируется по времени события, затем ID; ретенция 30 дней использует то же время.
- Frontend использует часовой пояс устройства во всех связанных представлениях.
  Наведение показывает точную дату, время и имя пояса. Различие дат
  «Загружен» и «Обработка завершена» допустимо: это разные события.

## Обновление существующей установки

Колонки добавляются существующим `ensure_column_migrations` при старте API.
Сначала запустить новый API и дождаться успешной миграции, затем обновить все
Celery-воркеры и beat, включая worker-artifacts. Старые воркеры продолжают писать
по старому контракту, поэтому смешанный состав версий не обеспечивает новую
семантику времени. Пуш рабочей ветки сам по себе не выполняет этот выкат.

Исторические уведомления сохраняют прежнее значение `created_at` как время
события. Для старых терминальных файлов без `finished_at` миграция один раз
использует `updated_at`; для состава старого кейса — `created_at`. Это приближение:
если метаданные раньше менялись, точное историческое время не восстанавливается.
Повторный запуск миграции заполненные даты не переписывает.

## Проверки

`tests/unit/api/test_notifications.py` проверяет повторы, новые попытки,
запоздавшие и конкурентные доставки, одинаковую семантику синхронного и
асинхронного upsert, время источника в API, переименование/повторное добавление
материала в кейс и повторяемость миграции. `test_ops.py` проверяет стабильную
длительность после переименования.

На фронтенде `format.test.ts`, `Timestamp.test.tsx` и `NotificationBell.test.tsx`
покрывают полночь, переход летнего времени, одинаковые UTC/offset значения,
локализацию, общий таймер, возвращение во вкладку и совместимость старого API.
