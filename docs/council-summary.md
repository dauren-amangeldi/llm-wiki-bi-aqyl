# Итоги консилиума

Обновлено 22.09.2026. Итог содержит только позиции экспертов и их ключевые
аргументы, собранные из сохранённой переписки. Генерация запускается явным
действием пользователя. Открытие вкладки и новые сообщения её не запускают.

## Контракт

- `GET /api/v1/twin/sessions/{id}/summary` возвращает `{"summary": null}`
  до первого запуска либо сохранённый результат. Вызовов модели нет.
- `POST /api/v1/twin/sessions/{id}/summary` принимает
  `{"language":"ru","previous_revision":null}` для первого запуска.
  Для обновления клиент передаёт ревизию показанного итога.
- Итог: `revision`, `source_seq`, `language`, `created_at`,
  `refresh_available_at`, `positions: [{persona_id, position, key_argument}]`.
  Время — ISO 8601 с часовым поясом. Язык нормализуется в ru/en/kk.

При несовпадении `previous_revision` с сохранённой ревизией сервер возвращает
готовый результат. Повтор запроса после потерянного ответа не оплачивает ещё
один вызов. Конкурирующие запросы блокируются транзакционным advisory lock
PostgreSQL по ID сессии; второй запрос получает `409 summary_in_progress`.

Повторная генерация разрешена через 15 минут после успешного сохранения или
раньше, если после `source_seq` появились содержательные ответы экспертов.
Вопросы пользователя, пустые и неуспешные ответы не снимают ограничение.
Преждевременный запрос получает `429 summary_cooldown` и `Retry-After`.

Модель получает весь допустимый транскрипт и должна кратко передать позицию
каждого высказавшегося эксперта, включая изменения мнения. Она не должна
добавлять новые факты, ссылки или согласие, которого не было в обсуждении.
Ошибочные ответы исключаются по флагу `failed` и старым локализованным текстам
ошибок. Старые сообщения `verdict` в контекст не включаются.

Нет содержательных ответов → `422 summary_no_replies`; больше 80 000 символов
в отфильтрованном транскрипте → `422 summary_too_long`. Это явный отказ, без
молчаливого обрезания. Вызов ограничен 75 секундами. Ошибка модели/валидации →
`503 summary_failed`; сырое сообщение провайдера клиенту не возвращается.
При ошибке старый итог сохраняется.

## Хранение и выпуск

`twin_summaries` содержит одну последнюю версию на сессию. Итог не добавляется
в сообщения и не увеличивает контекст следующих реплик. Оба маршрута используют
проверку доступа к сессии. Внешний ключ с `ON DELETE CASCADE` удаляет итог вместе
с сессией; удалённая во время генерации сессия не восстанавливается.

Сначала выпускается backend, затем frontend. Новую таблицу создаёт существующий
`Base.metadata.create_all` при запуске API; роль приложения должна иметь права
на создание таблиц, как при остальных стартовых миграциях проекта. Новой
переменной окружения не требуется. Генерация использует существующий LLM-клиент
с типом агента `twins` и ключ API-процесса; Celery в этом маршруте не участвует.

При ротации ключа для проверки всего продукта требуется пересоздать API и все
воркеры, включая `worker-artifacts`: ingestion и артефакты используют ключи
своих процессов. Перезапуск только API их окружение не обновляет.

## Проверки

Автотесты: `tests/unit/api/test_twin_summary.py` и
`tests/unit/agents/test_twin_summary.py`. Они проверяют доступ, повторные и
конкурирующие запросы, интервал обновления, новые ответы, ошибки, структуру
результата, язык, удаление сессии и сохранность прежнего итога.
Тесты с пересозданием схемы нужно запускать только в отдельной тестовой БД.

Ограничение качества: итог пересказывает реплики. Если исходный ответ эксперта
использовал нерелевантный фрагмент общей вики, отдельная генерация итога не
исправляет ошибку выбора источника. См. `qa-council-summary-2026-09-22.md`.
