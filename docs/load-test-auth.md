# Тестовые учётки и первый прогон Locust

Обычный вход AQYL остаётся через Keycloak. `allowed_users` ограничивает доступ
после проверки личности, но сам по себе не выдаёт токен. Для нагрузочного
клиента добавлен отдельный `POST /api/v1/auth/load-test/token`.

## Как это работает

- При старте API штатная идемпотентная миграция добавляет
  `allowed_users.load_test_enabled boolean NOT NULL DEFAULT false`.
  Прежние пользователи не получают тестовый вход.
- Только при включённом тестовом режиме seed создаёт
  `loadtest-0001@aqyl.test.invalid` (по умолчанию одну учётку).
  `LOAD_TEST_USER_COUNT` допускает 1–1000 отдельных идентичностей для будущих
  прогонов. Увеличение числа не запускает нагрузку.
- Locust передаёт email в JSON и общий секрет прогона в `X-Load-Test-Secret`.
  API проверяет секрет и отдельный флаг whitelist, возвращает bearer JWT на
  15 минут. Используется отдельный серверный ключ подписи, неизвестный Locust.
- Разрешены только синтетические адреса `loadtest-0001`…`loadtest-1000` в
  домене `aqyl.test.invalid`. Секрет не позволяет входить под email сотрудника.
- Роль всегда `employee`, даже если в БД этому тестовому email ошибочно
  выставили admin. В whitelist проверяются `blocked` и `load_test_enabled`
  при каждом защищённом запросе, включая уже выданные токены.
- Истечение токена требует нового тестового входа; SSO refresh/logout эти
  токены не обслуживают. Текущий короткий smoke укладывается в срок токена.
- Режим требует одновременно `AUTH_ENABLED=true`, `APP_ENVIRONMENT=test`,
  точный `PUBLIC_BASE_URL=https://aqyl.test.bi.group`, включённый флаг и два
  разных секрета длиной минимум 32 символа. По умолчанию режим выключен.
  Несовместимая конфигурация с включённым флагом останавливает запуск сервиса.
  При выключенном режиме endpoint возвращает 404, тестовые JWT не принимаются.

Вход тестовых пользователей не измеряет Keycloak/SSO. Общий секрет разрешает
вход во все активные тестовые учётки, поэтому выдаётся только оператору прогона.
Токены дают обычный пользовательский доступ на test; сам клиент текущего smoke
вызывает только перечисленные ниже маршруты без AI.

## Настройка тестового стенда

Один раз создать секреты локально, вне репозитория:

```sh
python3 scripts/create_load_test_env.py --output-dir "$HOME/.aqyl-load-test/20260929"
```

Скрипт создаёт файлы с правами 0600 и печатает только пути. Существующую папку
не перезаписывает. `server.env` — добавочные переменные для тестового API:
внести их в источник окружения деплоя, сохранив остальные существующие настройки.
Это не замена всего окружения и не файл для production. `login-secret` нужен
только локальному Locust; ключ подписи в Locust не копируется.

После публикации кода и обновления окружения перезапустить API. Миграция и
seed выполнятся при его старте; ручные INSERT и создание пользователей в SSO
не нужны. Seed не разблокирует и не включает повторно существующие строки.
В логах ожидать `startup_config.load_test_auth_active=true` и, при первом
создании, `load_test_users_seeded`. Значения секретов не логируются.

В этом репозитории push в `develop` запускает тестовый pipeline: собирается
общий образ из текущего кода, затем он устанавливается в `bi-aqyl-api`,
`bi-aqyl-worker` и `bi-aqyl-beat`. Отдельная правка воркера для пересборки не
нужна. Дождаться успешного deploy и проверить новую версию образа в логах.
Добавление переменных или перезапуск старого образа не добавляет новый маршрут:
код тестового входа тоже должен попасть в опубликованный коммит.

Функция включается только в окружении test. В prod/stage оставить
`LOAD_TEST_AUTH_ENABLED=false`; сам коммит миграции создаёт лишь неактивный флаг.

## Locust: один пользователь, один проход

Python 3.11+, отдельное окружение, зависимости `tests/load/requirements.txt`.
Штатные параметры headless/time limit: [документация Locust](https://docs.locust.io/en/stable/running-without-web-ui.html).

Проверки режимов авторизации без сетевых запросов выполняются отдельно:
`python tests/load/check_auth_modes.py` из окружения Locust. Они не включены
в общий pytest backend, чтобы необязательный Locust и его gevent-подмена
сетевых функций не меняли поведение остальных тестов.

```sh
python3 -m venv /tmp/aqyl-locust-venv
/tmp/aqyl-locust-venv/bin/pip install -r tests/load/requirements.txt

AQYL_PROFILE=preflight \
AQYL_RESULTS_DIR=/tmp/aqyl-locust-results \
/tmp/aqyl-locust-venv/bin/locust -f tests/load/locustfile.py \
  --host https://aqyl.test.bi.group --headless -u 1 -r 1 \
  --run-time 90s --stop-timeout 35 \
  --csv /tmp/aqyl-preflight --html /tmp/aqyl-preflight.html
```

`preflight` выполняет пять GET: health, readiness, auth/config и ожидаемые
отказы 401 для cases/auth/me без токена. Ожидаемый 401 — успешная негативная
проверка, а в серверном логе закономерно `outcome=rejected`.

### С существующей SSO-сессией сотрудника

Для одиночного smoke можно использовать действующий access token своей учётки.
Новый endpoint, миграция и включение тестового входа для этого не нужны.
Сохранить значение `bi_token` из Local Storage **тестового** AQYL во временный
файл вне репозитория с правами 0600. Допускается JWT либо JSON-строка, которую
хранит браузер. Сам токен не передавать в командной строке, чате или отчётах.

```sh
AQYL_PROFILE=readonly \
AQYL_ACCESS_TOKEN_FILE=/private/tmp/aqyl-smoke/access-token \
AQYL_RESULTS_DIR=/tmp/aqyl-locust-results \
/tmp/aqyl-locust-venv/bin/locust -f tests/load/locustfile.py \
  --host https://aqyl.test.bi.group --headless -u 1 -r 1 \
  --run-time 180s --stop-timeout 35 \
  --csv /tmp/aqyl-readonly --html /tmp/aqyl-readonly.html
```

Путь выше — пример; файл с токеном нужно подготовить заранее. Не задавать
одновременно `AQYL_ACCESS_TOKEN_FILE` и `AQYL_LOAD_LOGIN_SECRET_FILE`.
Клиент проверяет токен через `/auth/me`, сохраняет обычные права учётки и
использует только операции чтения. Тест не выполняет SSO-вход, refresh и logout.
При истечении токена прогон останавливается; обновить сессию в браузере и
повторить с новым токеном и новым run ID. После прогона удалить временный файл.

### С отдельной синтетической учёткой

После включения нового входа запустить защищённые сценарии:

```sh
AQYL_PROFILE=readonly \
AQYL_LOAD_LOGIN_SECRET_FILE="$HOME/.aqyl-load-test/20260929/login-secret" \
AQYL_RESULTS_DIR=/tmp/aqyl-locust-results \
/tmp/aqyl-locust-venv/bin/locust -f tests/load/locustfile.py \
  --host https://aqyl.test.bi.group --headless -u 1 -r 1 \
  --run-time 180s --stop-timeout 35 \
  --csv /tmp/aqyl-readonly --html /tmp/aqyl-readonly.html
```

Сначала preflight, затем проверка личности (в синтетическом режиме также login), A02 (главная),
A03 (лексический поиск), A04 (кейс), A05 (готовый текст), A06 (чтение готового
артефакта), A07 (чтение истории), A08 (чтение уведомлений). Это API-варианты
сценариев: визуальная проверка, SSO/logout/refresh, экспорты, отметка уведомлений,
редактирование, удаления и все генерации в этот smoke не включены.

ID берутся из ответов. Нужен хотя бы один доступный готовый кейс. Тестовая
учётка не видит личные кейсы и историю сотрудников. Отсутствующие сохранённые
артефакты/история явно отмечаются `skipped` в `coverage.json`; успешные HTTP не
означают, что отсутствующий сценарий прошёл. Новые данные скрипт не генерирует.

Ограничения: ровно один пользователь, только test URL, пауза 1 с между
запросами, максимум 60 запросов и один проход. На первой неожиданной ошибке
прогон прекращается с кодом 1. Большую нагрузку этим профилем запускать нельзя.
Locust — HTTP-клиент, не браузер: статические ресурсы/вёрстку он не проверяет
([документация](https://docs.locust.io/en/stable/writing-a-locustfile.html)).

Отчёты: стандартные CSV/HTML Locust и `<AQYL_RESULTS_DIR>/<run_id>/` с
`requests.jsonl`, `coverage.json`. Токены, секреты, тела и содержимое документов
в них не сохраняются. `X-Run-ID`, `X-Scenario-ID`, `X-Operation-ID`, `X-Request-ID`
передаются на каждом запросе. Пока JSON не разобран в Elastic, использовать
`message : "<run_id>"`; у каждого HTTP ожидаются started и handled.

## Завершение и отзыв доступа

Выключить `LOAD_TEST_AUTH_ENABLED` и перезапустить API — тестовые токены сразу
перестанут приниматься. Для одной учётки можно штатным `manage_access.py block`
поставить `blocked=true`; новый login и существующие токены получат 403.
При ротации `LOAD_TEST_SIGNING_SECRET` все прежние тестовые токены недействительны.
При ротации только login-секрета старые токены живут до expiry либо блокировки.
Повторный seed сохраняет блокировки. Существующие кейсы и историю он не удаляет.
