# AQYL: логи для нагрузочного тестирования

Изменения подготовлены локально 29.09.2026 поверх `096a5e6`.
Они не опубликованы на стенды. Locust и платные генерации в этой проверке не запускались.

## Идентификаторы прогона

Клиент теста передаёт эти заголовки во все запросы, включая опрос статуса:

| Заголовок | Значение |
| --- | --- |
| `X-Run-ID` | Один ID на весь прогон, например `aqyl-smoke-20260929-01` |
| `X-Scenario-ID` | Код сценария из карты маршрутов |
| `X-Operation-ID` | Один уникальный ID на отдельное прохождение сценария одним пользователем |
| `X-Request-ID` | Уникальный ID конкретного HTTP-запроса; можно не передавать — сервер создаст его |

Допустимы латинские буквы, цифры, `_`, `.`, `:`, `-`, длина до 128 символов.
Первый символ — буква или цифра. Некорректные значения не попадают в контекст.
Ответ возвращает `X-Request-ID`, в том числе при необработанном HTTP 500.
Если operation ID не передан, используется request ID.
Эти заголовки служат только для поиска логов и не предоставляют доступ к API.

Связь сохраняется через Celery headers: API → очередь → воркер → следующие задачи.
Ресурсы помечаются `file_id`, `case_id`, `document_id`, `artifact_id`,
`generation_id`, `session_id`, `consultation_id`, когда они известны обработчику.
ID запуска генерации (`generation_id`) позволяет связать повторный HTTP-запрос,
вернувший уже выполняющуюся задачу, с первоначальной генерацией.

## События

| Событие | Что измерять / проверять |
| --- | --- |
| `request_started` | Запрос принят приложением; незавершённые запросы можно найти по отсутствию финальной записи |
| `request_handled` | `method`, шаблон `route`, `status_code`, `duration_ms`, `outcome`, `response_complete` |
| `task_queued` | Публикация в брокер завершилась; есть `task_id`, `task_name`, `queue` |
| `task_enqueue_failed` | Задача не опубликована; есть тип ошибки и идентификаторы |
| `task_execution_started` | Воркер приступил к работе; `queue_wait_ms`, `retry_count` |
| `task_execution_finished` | Время выполнения и результат задачи, включая `failed` внутри успешного Celery-return |
| `ai_call_started` | Начало вызова AI-обёртки; `call_id`, модель, назначение |
| `ai_attempt_failed` | Неудачная попытка текстовой генерации и признак `retrying` |
| `ai_call_finished` | Итог AI-вызова: успех, ошибка, отмена или блокировка бюджетом |
| `llm_usage` | Единственный источник для суммирования измеренных токенов и оценочной стоимости |
| `usage_persistence_failed` | Запись локального usage.log не удалась; JSON-событие расхода уже отправлено в stderr |
| `budget_cost_incomplete` | В дневном журнале есть успешные вызовы без вычисленной стоимости |

Все эти события направляются в stderr в JSON. Стандартный Python logging также
получает JSON-формат. На рабочем стенде должен быть `LOG_LEVEL=INFO`.
Ключи API, Bearer-токены и чувствительные структурированные поля маскируются.
Общий HTTP-слой не записывает тело запроса, query string, cookies или Authorization.

### HTTP и SSE

`duration_ms` измеряется до окончания обработки ответа приложением, включая
поток SSE. `response_headers_ms` показывает время до начала ответа.
Для SSE дополнительно есть `first_event_ms`, `stream_events`, `stream_done`.
Первое событие может быть служебным статусом; это **не время первого токена LLM**.

HTTP 200 у SSE не означает успешную генерацию. Смотрите `outcome`:

- `success` — запрос/поток завершился успешно;
- `failed` — ошибка сервера, ошибка внутри SSE или таймаут обработки файла;
- `degraded` — использован резервный вариант, например SVG вместо картинки или ответ-заглушка эксперта;
- `rejected` — отказ/валидация/лимит либо содержательный отказ советника;
- `cancelled` — отмена или обрыв соединения;
- `incomplete` — поток закончился без финального события;
- `cached` — возвращён сохранённый итог Консилиума;
- `duplicate` — повторная загрузка или уже выполняющаяся генерация, без новой задачи.

В сценариях с очередью HTTP 202 означает лишь принятие запроса. Полный результат
проверяется через существующий маршрут статуса и `task_execution_finished`.
При SIGKILL/OOM финального события из погибшего процесса может не быть:
ищите начатые задачи без завершения и сопоставляйте с Grafana/событиями контейнера.

### Токены, время и стоимость AI

`llm_usage` теперь включает текст, embeddings, OCR каждой страницы, транскрипцию
аудио и генерацию изображения. Сохраняется также локальный JSONL `usage.log`.
Запись в файл и событие stderr — **две копии одного расхода**, объединяются по
`call_id`, не складываются вместе.

Измеренные поля: `input_tokens`, `output_tokens`, `cached_input_tokens`,
`reasoning_tokens` (если провайдер вернул), `audio_seconds`, параметры изображения.
Reasoning tokens уже входят в output tokens; повторно прибавлять их нельзя.
Если провайдер не вернул usage, токены остаются `null`, оценки «по длине текста» нет.
Для Whisper запрашивается структурированный ответ с длительностью аудио.

Для текста отдельно измеряются `semaphore_wait_ms`, `provider_duration_ms`,
`backoff_ms`, общее `duration_ms`, число `attempts`. `attempts` — попытки нашей
обёртки. Внутри SDK могут быть собственные повторы; их предельное число отражает
`sdk_max_retries`, а их время входит в `provider_duration_ms`.
Для embeddings каждая попытка каждой пачки получает отдельный `call_id`.

`cost_usd` — оценка по `PRICE_TABLE`, а не сумма из биллинга OpenAI:

| `cost_status` | Значение |
| --- | --- |
| `estimated` | Использованы настроенные тарифы и измеренные единицы |
| `estimated_uncached_upper_bound` | Cached tokens посчитаны по обычному входному тарифу: cached-тариф не настроен |
| `unknown_model` | Для модели нет тарифа |
| `missing_usage` | Провайдер не вернул необходимые единицы |
| `missing_rates` / `missing_media_rates` | Тариф настроен не полностью |

Неизвестная стоимость записывается как `null`, не как бесплатный вызов.
Ошибки/обрывы без usage также не доказывают нулевой расход: неизвестные списания
проверяются отдельно в биллинге провайдера. Подтверждённая успешная генерация
не повторяется только из-за ошибки записи локального usage.log.

Перед платным прогоном необходимо настроить `PRICE_TABLE` для **всех фактически
используемых моделей**. Значение переменной — JSON-объект с точными model ID.
Существующие тарифы в коде не менялись и здесь не подтверждаются как актуальные.

Поддерживаемые поля одной модели:

- `input`, `output`, `cached_input` — USD за 1 млн соответствующих токенов;
- `per_minute` — USD за минуту аудио, если цена считается по длительности;
- `image_input` — отдельный тариф за 1 млн входных image tokens, если они возвращены провайдером.

Для media с неизвестным разделением входных токенов стоимость может оставаться
неизвестной даже при наличии части тарифов. Не подставляйте тариф текстовой
модели вместо image/audio тарифа.

`GET /api/v1/stats` сохраняет прежние числовые поля для совместимости и добавляет
`unpriced_calls_today`: при значении больше нуля отображаемые суммы неполные.
Дневной BudgetGuard читает локальный usage.log. Это существующий механизм,
**не атомарный общий денежный лимит** между независимыми pod/воркерами.
Для нагрузочного прогона нужен отдельный согласованный бюджет и контроль
расхода по всем контейнерам; неизвестную стоимость нельзя считать нулём.

## Проверка в logs.bi.group после публикации

Нужно обновить и перезапустить API и все воркеры, участвующие в сценариях.
Перезапуск только API оставит старое логирование фоновых генераций.
Проверьте получение stderr обоих типов контейнеров в нужном data view.
Доставка и JSON-parsing в Elastic локальными тестами не проверены.

Если JSON разобран в поля верхнего уровня, фильтры KQL:

```text
run_id : "aqyl-smoke-20260929-01"
run_id : "aqyl-smoke-20260929-01" and event : "request_handled"
run_id : "aqyl-smoke-20260929-01" and outcome : ("failed" or "degraded" or "incomplete")
run_id : "aqyl-smoke-20260929-01" and event : "llm_usage"
request_id : "ID-конкретного-запроса"
generation_id : "ID-генерации"
```

Это ожидаемые имена полей приложения. Если collector кладёт JSON в `message`
или под префикс, реальные KQL-поля будут другими. Сначала найдите одну запись
по текстовому ID и проверьте её структуру; затем настройте JSON parsing/поля.

Для первого прогона: один пользователь, одна операция, одинаковый operation ID
на запуске и polling. Сверить HTTP → task_queued → task_execution_started →
llm_usage → task_execution_finished → конечный статус ресурса. Только после
этой сверки имеет смысл увеличивать число пользователей в Locust.

## Локальная проверка

134 теста прошли: общий HTTP/SSE слой, корреляция Celery (включая настоящий
Celery tracer), LLM/retry/budget, OCR/audio/image adapters и обработчики кейсов,
советника, Консилиума и артефактов. PostgreSQL был отдельным временным
контейнером; AI-ответы подменены. Финальный runner запрещал сетевые соединения,
кроме временной БД. Рабочий Redis не использовался.

Сценарии не запускались против test/stage/prod; отправка JSON в Elastic и
биллинг настоящей генерации остаются проверкой после публикации изменений.
